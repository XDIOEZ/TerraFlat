# FlatWorld Agent 协作指南

本文件定义 AI Agent 在 FlatWorld 项目中的默认工作方式。目标是让项目逐步转向 Vibe Coding：开发者描述目标、体验和限制，Agent 负责理解上下文、完成最小可靠实现、验证结果并清楚交付。

## 1. 项目速览

- 项目类型：Unity 2D 俯视角沙盒游戏。
- Unity 版本：`2022.3.62f3c1`，未经明确授权不要升级编辑器或核心包。
- 渲染管线：URP 14。
- 主要代码：`Assets/5_Scripts/`。
- 主要场景：`Assets/3_Scenes/`。
- 预制体、配置、资源：`Assets/2_Prefabs/`、`Assets/4_ScriptObjects/`、`Assets/Resources/`、`Assets/AddressableAssetsData/`。
- 开发资料：`开发文档文件夹/`。优先读取当前文档；`过时文件/` 只作历史参考。
- 核心代码程序集：`Data`、`GamePlay`、`UI`、`Editor`、`Effect`、`Tool`、`m_Utilitiles`。
- 常用能力包括 Input System、Addressables、Cinemachine、2D Navigation、Entities、MemoryPack、XLua 和行为树。先复用项目已有方案，不重复造轮子。

## 2. 核心原则

1. **先理解体验，再修改代码**：确认玩家会看到什么、触发什么、成功标准是什么。
2. **上下文优先**：先查调用方、数据来源、Prefab/Scene 绑定和相邻实现，不根据类名猜行为。
3. **最小可靠改动**：只改完成功能所需的文件，避免顺手重构、全局格式化和无关命名调整。
4. **保持兼容**：保护序列化数据、公开 API、存档格式、Addressables 地址、资源 GUID 和场景引用。
5. **验证闭环**：改动后检查编译、Console、相关测试和实际玩法路径；不能验证的部分必须明确说明。
6. **可回滚、可解释**：每次交付都应范围清晰，说明修改逻辑、验证结果和剩余风险。
7. **不伪造完成**：不虚构工具输出、测试结果、资源引用或 Unity Editor 状态。

## 3. Vibe Coding 工作流

### 3.1 接收需求

将自然语言需求整理为以下四项；能从项目中确认的内容直接确认，不反复追问：

- **目标**：要解决的问题或要实现的能力。
- **玩家体验**：玩家如何触发、看到和感受到结果。
- **验收条件**：哪些可观察结果代表完成。
- **限制**：不能改变的行为、数据、平台或性能边界。

只有在不同选择会明显改变玩法、数据结构、资源成本，或可能造成不可逆结果时才询问。其余情况采用最符合现有项目模式的假设继续，并在交付中列出假设。

### 3.2 调研

动手前执行与任务规模相称的调查：

1. 查看 `git status`，保护开发者未提交的改动。
2. 使用 `rg`/`rg --files` 搜索定义、引用、同类实现和相关资源。
3. 阅读目标脚本及其直接调用方；涉及 Unity 对象时继续检查 Scene、Prefab、ScriptableObject 和 Inspector 绑定。
4. 确认目标代码所属 `.asmdef` 及可用依赖，避免制造循环引用或跨层耦合。
5. 涉及玩法规则时查看 `开发文档文件夹/` 中对应的当前文档。

### 3.3 计划与实现

- 简单改动直接执行；跨系统任务先给出 3～6 个可验证步骤，并保持一次只推进一个步骤。
- 优先沿用已有 Manager、Module、Mod、SO、事件、对象池、行为树或 UI 基类模式。
- 先完成最小可玩纵切，再补边界处理和必要测试；不要提前搭建需求未使用的抽象层。
- 修改现有文件时保持局部风格一致。发现历史问题可记录，但除非阻塞当前需求，不扩大范围处理。
- 新增功能必须有明确入口、数据流和失败路径；临时代码、魔法数和调试开关不得悄悄进入正式路径。

### 3.4 验证

验证顺序如下，按改动风险选择足够的层级：

1. **静态检查**：搜索调用点，检查空引用、生命周期、订阅释放、程序集依赖和序列化兼容。
2. **Unity 编译**：触发 Asset Refresh/脚本编译，确认 Console 没有由本次改动引入的 error。
3. **自动测试**：存在相关测试时运行 EditMode/PlayMode 测试；修复缺陷时优先增加可复现的回归测试。
4. **场景验证**：在最小相关场景中走通“准备 → 触发 → 结果 → 重复/退出”的完整路径。
5. **回归检查**：检查与目标共享数据、事件或 Prefab 的相邻功能。

可以使用 Unity MCP/Editor 自动化完成编译、Console、场景和测试检查。不得只凭 IDE 编译成功就断言 Unity 行为正确；也不得把项目原有警告冒充为本次新增问题。若环境不支持某项验证，应写明“未验证”及人工验证步骤。

### 3.5 交付

最终回复使用中文，简洁包含：

- 完成结果；
- 修改文件；
- 验证结果；
- 未验证项或风险（没有则省略）；
- **修改逻辑**：在回复最后说明核心数据流、关键判断和为何采用该方案。

## 4. Unity 资产与工程安全

### 4.1 禁止直接修改的生成内容

不要编辑或提交以下 Unity/IDE 生成内容：

- `Library/`
- `Temp/`
- `Logs/`
- `obj/`
- `bin/`
- `.vs/`
- 自动生成的 `*.csproj`、`*.sln`

### 4.2 Scene、Prefab 与 `.meta`

- 优先通过 Unity Editor 或 Unity MCP 修改 Scene、Prefab、Animator、Timeline、Tilemap 和 ScriptableObject 资产。
- 除非改动极小、格式完全明确且可立即在 Unity 中验证，否则不要手工修改 Unity YAML。
- 移动、重命名或删除 `Assets/` 下的资源时必须连同 `.meta` 一起处理，保持 GUID 不变；优先在 Unity Editor 中操作。
- 不手写或猜测 GUID，不批量重新导入资源，不无故触碰无关 Scene/Prefab 造成 YAML 噪音。
- 新建资源后确认其 `.meta` 已由 Unity 正确生成；文本文件换行和编码保持项目现状。

### 4.3 第三方内容与包

- `Assets/Plugins/`、`Assets/TheKiwiCoder/`、`Assets/Packages/` 和外部 Package 默认为第三方区域。
- 除非需求明确要求或项目封装无法解决，不直接修改第三方源码；优先在 `Assets/5_Scripts/` 中通过适配、继承或扩展解决。
- 新增/升级 Package、改变 Project Settings、渲染管线、Input Actions 或 Addressables 配置前，先说明必要性和影响范围。

## 5. C# 与 Unity 编码约定

### 5.1 兼容与序列化

- 不擅自重命名或删除 `[SerializeField]`、public 字段、属性、事件、UnityEvent 方法和被 Scene/Prefab 引用的脚本类型。
- 必须重命名序列化字段时使用 `[FormerlySerializedAs]`，并验证旧资产仍能反序列化。
- 新字段显式写明访问级别。现有未标记 `private` 的字段按项目约定整理为 `public`；不要擅自收窄既有字段可见性。
- 运行时数据与配置数据分离；共享配置优先使用现有 ScriptableObject/数据层，避免把全局状态散落在 MonoBehaviour 中。
- 修改存档或 MemoryPack 数据结构时考虑旧版本兼容、默认值和迁移策略。

### 5.2 结构与命名

- 遵循相邻代码的命名风格，不为“更好看”批量重命名。
- 类内通常按“字段 → 属性 → Unity 生命周期 → public 方法 → private 方法”组织。
- 使用 `#region` 管理功能块。`#region`/`#endregion` 必须顶格，区域内部首尾保留空行，类内成员应纳入清晰的 region。
- Editor 代码只能进入 Editor 目录或 Editor-only 程序集，运行时代码不得依赖 `UnityEditor`。
- 尊重现有 `.asmdef` 边界；新增引用前先确认依赖方向，避免让底层 Data/Utilitiles 反向依赖 GamePlay/UI。

### 5.3 注释与日志

- 注释使用中文，解释“为什么”和约束，不机械复述代码。
- 字段使用简洁的行尾 `//` 注释；方法使用合适的 `///` 文档注释并包含必要参数说明；方法内部关键步骤使用精简 `//` 注释。
- `Debug.Log*` 必须包含上下文，如对象名、关键变量和当前状态，避免只有一段无法定位来源的字符串。
- 高频路径不要持续打印日志。临时调试日志在交付前删除，或通过项目已有调试开关控制。

### 5.4 Unity 运行时注意事项

- 遵循 `Awake → OnEnable → Start → OnDisable → OnDestroy` 生命周期，事件订阅与退订必须成对。
- Coroutine、Invoke、Tween、异步任务和对象池回收都要考虑重复启用、场景切换和对象销毁。
- 不在 `Update`/`FixedUpdate` 高频分配集合、字符串或产生无意义查找；缓存稳定引用，但不要用缓存掩盖生命周期错误。
- 正确区分 2D 与 3D 物理 API，物理移动放在合适的 FixedUpdate 路径。
- Unity 对象使用 Unity 的销毁/null 语义；从后台线程返回后，不直接操作 UnityEngine 对象。
- 公共玩法逻辑应尽量与表现解耦，便于 EditMode 测试；MonoBehaviour 保持编排职责。

## 6. Git 与改动边界

- 默认不覆盖、还原、暂存或提交开发者已有改动。
- 修改前后都检查 `git diff --check` 和目标文件 diff，警惕编码变化、整文件换行变化和资源序列化噪音。
- 不使用破坏性 Git 命令；不删除无法确认归属的文件。
- 不把大体积备份、构建产物、日志或临时测试资源纳入变更。
- 未经要求不创建分支、不提交、不推送。

## 7. 完成定义（Definition of Done）

只有同时满足以下条件才称为完成：

- 验收条件已转化为可观察行为并实现。
- 变更范围聚焦，没有覆盖用户已有修改。
- Unity 编译无本次新增 error。
- 相关测试已通过，或明确说明为何没有/无法运行。
- 相关 Scene/Prefab/ScriptableObject 引用有效，序列化数据未意外丢失。
- 重复触发、空数据、对象销毁、场景退出等关键边界已考虑。
- 没有遗留临时日志、占位实现、静默异常或未说明的 TODO。
- 最终回复末尾包含“修改逻辑”。

## 8. 推荐的需求表达模板

开发者可以只描述想法，Agent 负责补齐上下文；需要更稳定结果时可使用：

```text
目标：
玩家体验：
验收条件：
不能改变：
参考对象/场景（可选）：
```

示例：

```text
目标：工作台制作完成后给玩家明确反馈。
玩家体验：点击制作，进度结束后物品进入背包，同时播放一次音效和飘字。
验收条件：材料足够时只产出一次；背包满时不扣材料并提示；连续点击不会重复制作。
不能改变：现有配方和存档结构。
参考对象/场景：Module_WorkBench，GameStartScene。
```
