# FlatWorld Git 提交

## 适用时机

- 在一个功能、系统切片或完整修复已经完成后运行一次，不要在每个小编辑后提交。
- 当前任务明确要求“不要提交”时停止；用户明确要求立即提交时，可跳过复杂度判断，但仍必须通过范围和安全检查。
- 本 Skill 只负责本地 `git commit`，不自动 push、合并、rebase、reset、clean 或修改历史。

## 提交边界

只有同时满足“本次任务已完成”和“改动可以安全隔离”时才提交。复杂度达到以下任一条件即可视为达到边界：

- 一个完整的用户可见功能或系统切片已经闭环，且包含运行时代码与其必要的配置、Prefab、资源、编辑器接线或数据定义。
- 改动跨越两个以上逻辑层，或涉及公共接口、存档/序列化结构、网络协议、输入契约、核心生命周期等高影响边界。
- 一个跨文件的完整 Bug 修复已经形成稳定的可回滚点；即使只有一个文件，只要它改变了权威配置、公共契约或独立运行时行为，也可以提交。

以下情况通常不提交，保留改动等待同一系统的后续工作：文档或格式整理、单个低风险文案/数值调整、临时调试代码、未完成的 WIP、仅生成文件变化，或无法确认属于本次任务的改动。

## 范围保护

1. 先查看 `git status --short`、`git diff --stat` 和相关路径差异；若任务开始前已有工作区改动，将其视为受保护内容。
2. 只根据本次对话实际修改的文件建立提交清单，禁止使用 `git add -A`、`git add .` 或 `git commit -am` 扩大范围。
3. 对每个候选文件检查差异；一个文件同时混有旧改动和本次改动时，不要提交该文件，除非能安全拆分，否则暂停并说明需要用户处理。
4. Unity 新增或改名的资源应连同对应 `.meta` 一起检查；不要提交 `Library/`、`Temp/`、`Logs/`、`UserSettings/`、密钥、临时目录或其他生成物。

## 提交流程

达到边界后按以下顺序操作：

```powershell
git status --short
git diff -- <本次任务文件>
git add -- <本次任务文件>
git diff --cached --check
git diff --cached --stat
git diff --cached -- <本次任务文件>
git commit -m "<type>: <简短说明>"
git status --short
```

- 提交信息优先使用 `feat:`、`fix:`、`refactor:`、`data:` 或 `chore:`，说明具体系统和结果；不要使用无信息的“提交”“修改”等描述。
- 提交前必须确认暂存区只包含本次任务；发现范围不明、冲突、钩子失败或身份配置问题时停止，不使用 `--no-verify`，也不擅自修复无关问题。
- 不自动运行游戏测试、构建或重型验证；沿用当前任务已完成的静态检查和 Unity Console 检查结果。提交后向用户报告提交短哈希、提交说明，以及仍保留的未提交文件（如有）。

## 未达到边界时

不创建空提交、不暂存文件，并明确说明当前改动仍是未完成或低复杂度工作区，等待后续同一系统的改动；下一次该系统任务完成时重新评估整个任务范围。
