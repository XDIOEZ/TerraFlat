# FlatWorld Git 操作规范

## 总原则

- 执行 Git 写操作前先查看当前分支、`git status --short` 和相关差异，不能根据聊天里的旧状态直接操作。
- 用户没有明确要求提交、推送、重置、变基或改写历史时，不主动执行对应操作。
- 不使用 `git add .`、`git add -A` 或 `git commit -am` 把无关改动一起提交；只暂存当前任务确认过的文件。
- Unity 新增、删除或移动资源时，必须同时检查对应 `.meta` 文件。
- 不提交 `Library/`、`Temp/`、`Logs/`、`UserSettings/` 等生成目录或临时文件。

## 提交信息规范

- **提交说明主体必须使用中文。** 可以保留 `feat:`、`fix:`、`refactor:`、`data:`、`docs:`、`chore:` 等类型前缀，但前缀后的内容必须用中文描述。
- 提交标题要说明“改了什么 + 达成什么结果”，不能只写“修改”“更新”“修复问题”“调整代码”这类无信息文本。
- 标题保持简洁，但必须覆盖本次提交的主要目的，不要只写某个文件名。
- 改动较多时可以增加中文提交正文，用 2～4 条概括关键变化；不要把每个文件逐条抄成流水账。
- 提交前必须根据实际 `git diff` 生成说明，不能只根据用户描述或聊天记忆编写提交信息。

推荐格式：

```text
feat: 新增木弓与多材质箭矢配置

- 接入木弓及木、石、铜、铁箭矢资源
- 补充物品定义与合成配置
- 保持现有武器模块和资源加载流程复用
```

不推荐：

```text
update files
修改代码
修复一些问题
提交最新内容
```

## 提交流程

用户明确要求提交后，按以下顺序处理：

```powershell
git status --short
git diff -- <本次任务文件>
git add -- <本次任务文件>
git diff --cached --check
git diff --cached --stat
git diff --cached -- <本次任务文件>
git commit -m "<类型>: <中文提交说明>"
git status --short
```

- 提交前确认暂存区只有本次任务内容。
- 提交完成后告诉用户：提交短哈希、中文提交说明、是否还有未提交改动。
- `push` 必须由用户明确要求；普通“提交”只代表创建本地 commit。

## 拉取与冲突

- 拉取前先检查工作区和本地/远端分支关系；有未提交改动时先保护这些改动，不直接覆盖。
- 出现冲突时查看双方实际改动后手工合并，不能为了快速结束而无脑使用整文件 `ours` 或 `theirs`。
- `reset --hard`、强制推送、rebase、历史改写等高风险操作，必须由用户当前任务明确授权后才能执行。
