# FlatWorld Git 提交复查与优化

用户要求“检查/复查/优化最近几个提交”时使用本 Skill。审查对象是**提交带来的游戏行为变化**，不只是提交说明或代码风格；重点是正确性、性能、模块边界和回归测试。

## 1. 确定范围，保护现场

- 先执行 `git status --short --branch` 和 `git log --oneline -n <N>`；优先使用用户指定的数量、SHA 或范围，未指定时默认从 `HEAD` 查最近 1 个提交。记录分支、提交 SHA、未提交与已暂存修改，不擅自拉取远端。
- 逐个检查 `git show --stat --find-renames <SHA>`、`git show --format=fuller --find-renames <SHA> -- <路径>`；同时看范围的**最终净差异**，避免把后续提交已修好的问题当成现存 Bug。
- 合并提交先看第一父提交到合并结果的差异；涉及冲突解决时再对照另一父提交，不把合并日志直接当作功能修改。
- 历史证据用 `git show <SHA>:<路径>` 或提交间 `git diff` 读取，当前行为以 `HEAD` 和工作区分别核对。**工作区脏文件不等于提交内容**，禁止覆盖、混合或误提交别人的改动。

## 2. 按风险复查，而非逐行挑风格

1. **行为与回归**：调用方、状态流转、对象销毁、初始化/退出、场景切换、存档、联机权威、失败回滚及边界值；区分新引入的问题和既存问题。
2. **性能与资源**：每帧/每实体/每区块热路径中的重复遍历、GC 分配、算法复杂度、同步加载、频繁创建销毁及事件订阅泄漏；性能结论尽量由次数、规模、Profiler 或测试支撑，静态推断明确标为风险。
3. **结构与数据**：是否绕过原有模块接口、重复维护状态或制造特殊分支；检查关联 Prefab、配置、序列化字段、Shader、Unity `.meta` 和跨系统契约。
4. **测试有效性**：覆盖正常、异常、边界和关键集成链路；不能将“能编译”“无报错”“已有测试入口”当成功能已验证。

只记录能指向具体提交、文件位置及影响机制的问题，按 `P0 阻断/丢数据 → P1 功能错误 → P2 明确隐患 → P3 可选改进` 排序。对无法证实的问题说明缺少什么证据，不为了凑数量提问题。

## 3. 修复真实问题

- 先追踪变更处及其上下游，再读取对应 `.agents/skills/flatworld-*/SKILL.md`；Bug 根因与现场按 [已知 Bug 修复](../flatworld-fix-loop/SKILL.md) 处理。
- 在**当前代码**上修复仍然存在的缺陷；优先修正式规则、职责和接口，避免只加判空、吞异常、额外轮询或复制规则掩盖问题。保持修改聚焦，避免借复查进行无关大重构。
- 优先处理已证实的 P0/P1、可安全消除的 P2；P3 只在收益清楚且代价可控时修改。历史问题已被后续提交解决的，不重复修复。
- 用户在 PlayMode 时只做静态修改，不暂停、退出或重启 Unity。已有未提交修改与修复相交时先核对来源；无法安全区分则保留现场并报告阻碍，不强行覆盖。

## 4. 验证与提交

- 检查实际 diff、`git diff --check`、相关引用与数据格式；如修改玩法代码，按 [Lua 测试](../flatworld-lua-testing/SKILL.md) 和 `systems.catalog.json` 选用 `run_suite.py --changed <修改路径>`，必要时补对应 Lua 断言，再运行关键集成。Unity 正在 PlayMode 或测试环境不可用时注明**未运行**，不可写成通过。
- 测试失败读取报告和首个失败证据，修根因后重新验证；不通过禁用测试、放松断言来制造通过。耗时较大的场景测试按相关性执行，不盲目全量重跑。
- 依照 [Git 提交](../flatworld-git-commit/SKILL.md) 仅暂存本轮修改、检查暂存 diff，并**新建本地修复提交**；不 `amend`、`reset`、`rebase`、`push` 或改写被审查的历史。纯文档修改按该 Skill 的提交门槛处理。

## 5. 简短交付报告

按「**复查范围 → 发现（严重度、SHA、文件:行、原因）→ 已修复内容 → 测试结果 → 剩余风险 → 新提交短 SHA**」汇报；没有确认的问题就明确说没有，不臆造性能收益或测试结果。若只做了审查、没有值得改的内容，不制造空提交。
