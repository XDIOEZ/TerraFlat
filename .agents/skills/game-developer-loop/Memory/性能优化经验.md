# DeveloperLoop 性能优化经验

核实日期：2026-10-06。

## 先锁定可比较条件

- 整帧耗时、FPS、GC 总量只有在实体数量、行为状态、时段、天气和加载区块基本一致时才适合做前后百分比比较。
- 条件对不齐时，不用全局均值证明优化；改用同一调用链的 Profiler Marker、GC.Alloc 路径、调用次数和功能行为做定向验收。

## Job 调度

- 感知这类“本帧收集请求、下一帧消费结果”的 Job，应在最后一个请求提交后尽早 `Schedule`，把剩余帧时间留给 Worker；不要无理由拖到 `LateUpdate`。
- 验证重点不是只看 Job 自身耗时，而是看下一帧 `Complete()` 的等待时间。当前样本中 `ItemMgr.Update.PerceptionComplete` 的中位等待约 `0.0003 ms`，同时真实导航和附近 AI 继续工作。
- Profiler Marker 名称必须跟真实阶段同步，否则后续会被旧的 `LateUpdate` 标签误导。

## 高频事件与 UI

- UnityEvent / UltEvent 若携带值类型参数，高频无状态变化调用可能产生装箱和分发成本。先判断状态是否真的改变，只在边沿变化时发事件。
- HUD 高频刷新不要每次遍历层级找控件；面板实例稳定后缓存 Slider/TMP 引用，销毁或换面板时清缓存。
- 数值文本优先使用 TMP `SetText` 的数值重载，避免插值字符串和格式化字符串临时对象。
- 简单状态条过渡不必为每次刷新创建 DOTween Tween/闭包；可复用结构体状态，并由面板生命周期持有的一条长期协程逐帧推进。不要把纯视觉补间反向绑进 0.1 秒业务 Tick，否则过渡会失去原有逐帧平滑度。改完必须实看 GameView，确认数值、过渡和面板生命周期仍正常。
- `MonoBehaviour` 类型的静态字段初始化器不要读取 `Resources` / 主题目录等 Unity API。组件构造阶段可能触发类型初始化，Unity 会报 “Load is not allowed to be called from a MonoBehaviour constructor”。运行时主题色改用静态属性，在真正刷新 UI 时延迟读取。

## 角色渲染效果

- 静态或事件驱动的 MPB 效果不应强制每帧重新提交。Setter 改变目标值时标脏，平滑过渡过程中只有实际输出变化时继续标脏。
- 把 `RequiresContinuousRendering` 设为 false 前，必须读控制器契约确认 `PrepareFrame` 仍会每帧执行；当前控制器会先执行 `module.UpdateFrame()`，再根据版本决定是否提交 Renderer，因此过渡不会被冻结。

## Profiler 与视觉验收

- 项目的 PuerTS Unity MCP 会把当前 Editor HTTP 地址写入 `.puerts-unity-mcp/instances.json`；性能分析优先用其中的真实 `httpUrl` 调 `editor.profiler.capture`，报告直接落到 `.puerts-unity-mcp/perf-reports/`。
- GC 优化用 `GC.Alloc` 路径验证最可靠。例如本轮旧 12 帧证据里的转身路径为 `3312 B / 138` 次；先把事件收窄到真实翻面后降到 `96 B / 4` 次，再确认两个 TurnBody Prefab 的持久监听均为空，把 `UltEvent<Vector2>` 换成 C# `Action<Vector2>` 后，最终 266 帧 `FlatWorld.Module.Mod_TurnBack` 为 `0 B / 0` 次。此类按调用链核对的结论比跨场景比较整帧 GC 更可信。
- GamePlayMCP 结构化状态负责功能事实，GameView 截图负责材质、阴影、UI、遮挡等纯视觉验收；两者都通过才算本轮闭环。
