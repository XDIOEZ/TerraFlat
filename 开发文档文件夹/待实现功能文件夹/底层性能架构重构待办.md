# FlatWorld 底层性能架构重构待办

## 1. 系统定位

本文只记录已经接近现有架构性能上限、继续做局部微优化收益会快速递减的系统。目标不是继续压几个函数的毫秒数，而是更换底层数据组织或算法，让高视距、大世界和高实体数量下仍能继续扩展。

当前项目仍处于开发阶段，首轮重构**不要求兼容旧实现、旧内部 API 或旧运行时缓存结构**。新架构完成并通过真实 Play Mode 验收后，可直接删除被替代的旧路径，避免双实现长期并存。

### 当前实测依据

- ChunkTilemapRenderer：单 Chunk 平均约 155ms，P95 约 245ms。
- ChunkNavigationBinder：单 Chunk 平均约 64ms，P95 约 159ms。
- terrain.cells：单 Chunk 平均约 599ms，P95 约 1015ms。
- 河流 Region 首次完整计算约 7.7s。
- ChunkNaturalItemRenderer：单步 P95 约 112ms。
- 当前 AI 数量很少，不是本轮底层重构重点。

这些数据用于确定方向，不作为未来版本的固定性能基线。每项重构开始前重新采样一次，完成后做同场景对比。

## 2. 首批重构总览

| 编号 | 优先级 | 系统 | 底层方向 | 目标 |
| --- | --- | --- | --- | --- |
| R01 | P0 | 地形生成 | Chunk 批量数据生成 + Job/Burst + 连续数组 | 消除逐 Cell 重复高成本计算 |
| R02 | P0 | 地形渲染 | Chunk Tile Buffer / Chunk Mesh，替代每 Tile BRG Instance | 地形表现成本从“格子数”转向“Chunk 数” |
| R03 | P0 | 河流水文 | 宏观水文图 + 局部细化 + 可复用 Region 缓存 | 消除进入新区域时秒级冷启动 |
| R04 | P1 | 世界导航 | Chunk-native 导航块 + Portal Graph + 局部 FlowField | 避免全局稀疏格字典成为核心瓶颈 |
| R05 | P1 | 自然物实体 | Data Entity + 批量表现 + 按需 GameObject Promotion | 世界自然物数量不再受 GameObject 数量限制 |

建议按 R01 → R02 → R03 → R04 → R05 分阶段实施。可以提前做接口设计，但不要同时大改五套权威数据。

## 3. R01 · P0 · 地形生成数据导向化

### 3.1 当前问题

当前 DeterministicChunkGenerator 以 Cell 为中心生成地形。单格会重复执行高度、降水、温度、Biome、河流、邻域条件、草地等计算，并逐项写入多层环境数据。

这套结构即使继续减少字典查询、减少函数调用，也仍然受限于“每个格子独立完成完整生成流程”的算法形态。

### 3.2 目标架构

改为以 Chunk 为最小生成批次：

~~~text
ChunkGenerationJob
    ├─ Height[]
    ├─ Precipitation[]
    ├─ Temperature[]
    ├─ Moisture[]
    ├─ Hydrology[]
    ├─ Biome[]
    └─ TerrainCell[]
              ↓
        一次 Seal / Commit
~~~

- 热数据使用连续数组或 NativeArray，不在 Cell 热循环中通过字符串 Dictionary 查层。
- Noise / Climate 输入按 Chunk 批量采样。
- 能 Burst 的纯数学阶段进入 Job/Burst；Unity 对象和资源解析留在主线程冻结阶段。
- 邻域规则优先复用已生成的局部采样窗口，不允许为单格条件反复重跑完整气候采样。
- 生成结果仍保持固定 Seed、确定性和当前 WorldModel 纯 C# / 无 Unity 对象边界。

### 3.3 首轮实现

- [ ] 将地表生成数据拆为固定布局的连续生成缓冲，不再用字符串层查找作为热路径。
- [ ] 将 Height / Climate / Biome 主循环改为 Chunk 批量计算。
- [ ] 将可并行纯数学阶段迁入 Job/Burst。
- [ ] 保持最终 ChunkTerrainData 作为权威状态，不把 Job 临时数据暴露给玩法层。
- [ ] 增加分阶段 Profiler Marker，至少区分 Noise、Biome、Environment Write、Ecology Input。
- [ ] 用同 Seed 对照新旧结果；新架构确认后删除旧逐格生成主路径。

### 3.4 完成条件

- 高视距连续移动时，后台生成不再长期形成明显队列饥饿。
- 普通 Chunk 的 terrain.cells P95 相比重构前有数量级明显下降，而不是仅下降个位数百分比。
- 固定 Seed 下结果稳定，取消任务和换世界不会提交过期结果。

## 4. R02 · P0 · 地形渲染改为 Chunk Buffer / Chunk Mesh

### 4.1 当前问题

现有 BRG 已经避免大量 SpriteRenderer / TilemapRenderer，但基础地形仍保持“一个 Tile 对应一个 BRG Instance”的模型。

首次绑定一个 Chunk 时会对大量格子执行 SetVisual / ClearVisual，并持续产生：

- Owner / Slot Dictionary 查询。
- Batch 查找与实例 Add / Update。
- 可见列表脏标记。
- 大量独立 CPU → GPU 实例数据维护。

因此继续优化 SetVisual 本身会逐渐接近天花板。

### 4.2 目标架构

基础地形改为：

~~~text
Chunk TerrainData
      ↓
TileId / Layer Buffer
      ↓
固定 Chunk Grid Mesh
      ↓
Shader 从 Atlas / Buffer 读取每格视觉
~~~

- Ground / Liquid / Back / Blocking 等规则层优先按 Chunk 数据上传。
- 一个 Chunk 每层尽量只保留固定少量 Draw，而不是按格实例化。
- 单格变化只更新 Buffer 对应索引，不删除 / 新增实例。
- 高度、岸线、液深、流向等继续作为格数据写入 Chunk Buffer。
- Chunk 边界变化只更新共享边需要的数据段。
- 动态机械、角色、掉落物等不强行塞进地形 Chunk Mesh。

### 4.3 首轮实现

- [ ] 先为 Ground 做一套独立 Chunk Buffer Renderer 原型。
- [ ] 保留当前 Sprite Atlas / Tile Catalog 身份映射，Shader 读取稳定 Tile Visual Index。
- [ ] 支持单格增量上传和整 Chunk 初始上传。
- [ ] 支持相机裁剪，不因 Chunk 已加载就必须提交不可见 Draw。
- [ ] Ground 稳定后迁移 Water / Back / Blocking 视觉层。
- [ ] Blocking 的物理碰撞仍与视觉解耦；不要为了新渲染路径复制第二份权威地形。
- [ ] 完成迁移后删除基础地形的逐 Tile BRG Instance 路径。

### 4.4 完成条件

- ChunkTilemapRenderer 不再出现单 Chunk 百毫秒级同步绑定。
- Chunk 初次显示成本主要由一次 Buffer 构建 / 上传决定。
- 单格地形变化不会触发整 Chunk 实例表重建。
- 高视距下 CPU 表现成本随 Chunk 数增长，而不是随可见 Tile 实例数线性放大。

## 5. R03 · P0 · 河流改为分层水文

### 5.1 当前问题

高度河网首次进入新的 Region 时需要执行完整区域求解，当前一次 Region 计算可达到约 7.7 秒。之后缓存命中很快，因此问题不是常态查询，而是首次求解粒度过大。

继续优化几个内层循环仍无法消除“进入新 Region 必须一次算完整张河网”的结构性延迟。

### 5.2 目标架构

~~~text
世界级 / 大区级宏观高度
          ↓
     Macro Hydrology
  主流向 / 汇水盆地 / 出口
          ↓
      River Corridor
          ↓
玩家附近 Chunk 局部细化
~~~

- 宏观层只保存决定河流拓扑所需的低分辨率数据。
- Chunk 生成只细化与当前 Chunk 有关的河段，不临时求解完整高分辨率 Region。
- Region 水文结果可跨 Chunk、跨后台任务复用。
- 世界关闭或全部需求取消时正确释放；单 Chunk 取消不能误杀仍被其它 Chunk 使用的共享水文任务。

### 5.3 首轮实现

- [ ] 定义低分辨率 Macro Hydrology 数据结构和稳定 Region Key。
- [ ] 将主河道拓扑与 Chunk 内可视河道细化分离。
- [ ] Chunk 生成只请求所需水文走廊。
- [ ] 为玩家活动窗口增加有限预热，不阻塞世界主线程。
- [ ] 保留河流、湖泊、流向和水深当前玩法语义。
- [ ] 新算法稳定后删除旧完整 Region 高分辨率冷启动路径。

### 5.4 完成条件

- 新区域首次进入不再出现数秒级单任务占用。
- 河流边界跨 Chunk 连续，固定 Seed 下稳定。
- 取消、快速移动、跨维度时没有废弃水文任务长期占用生成线程。

## 6. R04 · P1 · 导航改为 Chunk-native 分层导航

### 6.1 当前问题

当前核心导航仍依赖全局 Dictionary<Vector2Int, WorldNavigationCell>。Chunk 注册要逐格写入全局表，且已有路径中单格变化可能触发整 Chunk 重新注册。

先做增量更新可以解决近期尖峰，但从长期规模看，全局稀疏格字典仍会成为容量、缓存局部性和远距离寻路的上限。

### 6.2 目标架构

~~~text
ChunkNavigationBlock
    └─ NativeArray<Cell>
          │
          ├─ 本 Chunk FlowField / Local Path
          │
          └─ Portal
               ↓
         Chunk Portal Graph
~~~

- Chunk 内导航使用连续数组。
- 跨 Chunk 长距离寻路先走 Portal Graph，只在起点、终点和必要局部区域细化到 Cell。
- FlowField 缓存按 Chunk / Goal 复用，不为每个 AI 重复全局搜索。
- Terrain / Liquid / Occupancy 变化按局部脏区更新。
- 世界拓扑 Wrap 继续作为底层 Domain 规则统一处理。

### 6.3 首轮实现

- [ ] 先把 ChunkNavigationBinder 改成 Cell / Batch 增量更新，停止单格变化整 Chunk 重建。
- [ ] 新增 ChunkNavigationBlock 连续存储，作为后续正式权威导航数据。
- [ ] 建立相邻 Chunk Portal。
- [ ] 远距离路径切换到 Portal Graph + Local Refinement。
- [ ] 现有 AI 移动 API 尽量保持调用语义稳定，内部替换导航后端。
- [ ] 新后端覆盖正式玩法后删除全局 Cell Dictionary 的核心权威职责。

### 6.4 完成条件

- 单格建筑、液体或地形变化只更新局部导航。
- 高加载范围下导航注册不再出现百毫秒级 Chunk 尖峰。
- AI 数量提升后，远距离寻路成本主要与经过的 Chunk / Portal 数有关，而不是整个加载格网规模。

## 7. R05 · P1 · 自然物改为数据实体 + 按需实例化

### 7.1 当前问题

树木、矿石、植物等自然物如果长期以 GameObject + Transform + 多 Component 存在，即使使用对象池、降 Tick 和显隐管理，也最终会遇到 Unity GameObject 数量带来的 CPU、内存和生命周期成本。

当前自然物单个实例化步骤已经能出现百毫秒级尖峰，继续只优化对象池无法突破这一类上限。

### 7.2 目标架构

~~~text
远处 / 普通状态
NaturalEntityData
       ↓
批量 Sprite / BRG / ECS Presentation
       ↓
玩家靠近且需要交互
Promotion
       ↓
完整 GameObject
       ↓
离开交互范围
Demotion
~~~

- 普通树、矿石、植物默认只是数据，不持有完整 GameObject。
- 只有需要碰撞、受击、交互、动画或复杂模块时 Promotion。
- Promotion / Demotion 不改变稳定实体身份和权威状态。
- 掉落物继续遵守现有 ECS 掉落体系，不重新退回 GameObject-per-drop。

### 7.3 首轮实现

- [ ] 选一种最简单自然物作为模板，例如普通树或矿石。
- [ ] 定义可持久化 NaturalEntityData 与稳定 ID。
- [ ] 增加批量静态表现，不创建 Item GameObject。
- [ ] 玩家靠近或发生交互时创建完整 Item / Actor 壳。
- [ ] 离开后将生命、成长、采集等必要状态写回数据实体并回收 GameObject。
- [ ] 验证区块卸载、保存、重新加载、自然物删除差量和季节变化。
- [ ] 模板稳定后再迁移其它自然物。

### 7.4 完成条件

- 大量未交互自然物不再产生等量 GameObject / Transform / Component。
- 玩家靠近、攻击、采集、离开后的状态连续。
- 自然物密集 Chunk 的初次显示不再由大量 GameObject 实例化决定。

## 8. 配套优化，不作为底层重构主体

以下项目应该先做，但它们本身不是下一代架构：

- [ ] 删除 Commit 阶段当前无消费者的 ComputeStableHash，需要 Hash 的快照入口按需计算。
- [ ] 给当前 BRG 增加 Bulk Submit，作为 R02 完成前的过渡优化。
- [ ] 将 ChunkNavigationBinder 的变化处理先改为增量更新，作为 R04 的第一步。
- [ ] 将 ChunkCommitted 从全局广播逐步改为按 Chunk 地址 / 邻域定向通知。
- [ ] 继续保留流送阶段耗时埋点，禁止用“看起来不卡了”替代前后数据。

这些优化如果与对应底层重构立即衔接，可以直接作为新架构的迁移步骤，不必保留旧兼容层。

## 9. Agent 实施规则

- 一次只主攻一个编号，完成真实 Play Mode 验收后再进入下一项。
- 开工前先记录同场景性能基线，至少包含平均、P95、最大值以及 GC。
- 不允许只把同步工作挪到另一个帧或另一个队列就宣称完成；必须确认总工作量或关键路径延迟实际下降。
- 后台 Job 不得访问 UnityEngine Object、GameObject、MonoBehaviour、TileBase、Material 等主线程对象。
- WorldModel 继续保持纯数据权威；渲染、导航和 GameObject 都是消费层。
- 不为旧内部实现维护双路径。新实现覆盖正式运行链并验收后，删除旧代码。
- 每次重构都检查取消、快速移动、跨 Chunk、退出世界、F5 和重新进入世界的资源释放。
- 发现新的可复用架构约束时同步对应 .agents/skills/flatworld-* Skill，保持 Skill 简洁。
