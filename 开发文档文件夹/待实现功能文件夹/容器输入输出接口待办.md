# 容器输入输出接口待办

## 1. 系统定位

为能存放物品或液体的游戏物品提供统一的输入、输出能力，让动物、传送带、管道、抽水器等调用方通过容器能力转移内容，不按箱子、瓦罐等具体物品名称分别写逻辑。MOD 容器与 MOD 搬运设备必须走同一结构，不作为事后兼容项。

这里的“统一”指发现端口、查询可转移量、校验、提交和返回结果遵循同一流程；物品数量、容器液体份数、世界液深仍是不同数据和单位，不强制塞进一个无类型的数量字段。本文件规划接口与接入顺序，未表示这些设备或接口已经实现。

现有基础：箱子等使用 `Mod_Inventory` / `Inventory_Data`；瓦罐等使用 `Mod_WaterVessel`，其中液体以稳定 `LiquidId` 和浮点份数保存；世界水源由独立 Liquid 层维护，通过 `WorldLiquidSourceResolver` 识别、`WorldLiquidSystem.TryPump` 实际抽取。现有 `IInventory` 只提供默认目标库存，不是本计划需要的输入输出契约。

## 2. 容器端口

### 2.1 通用转移流程

```text
调用方找到源输出端口与目标输入端口
→ 查询源内容、目标余量及双方规则
→ 计算双方都能接受的实际转移量
→ 在权威运行态提交一次转移
→ 返回实际转移量与失败原因，通知双方刷新和保存
```

- [ ] 定义可由 Item / Module 查询的容器端口契约。端口明确支持输入、输出或双向；没有对应能力的物品不暴露端口。
- [ ] 转移请求带内容种类、稳定内容 ID、请求量、调用者、来源/目标和用途；返回实际转移量与明确失败原因。调用方不得把预检结果当作已提交结果。
- [ ] 物品端口使用物品实例数据并遵守现有 `ItemStack.Amount` 与最小转移单位规则；液体端口使用稳定 `LiquidId` 与明确标注单位的数量。两类端口共享流程，但保留各自的承载数据和校验规则。
- [ ] 多库存或多槽容器以稳定端口 ID 指向允许输入/输出的库存或槽位；不要默认把 `Mod_Inventory` 的第一个库存、制作输入槽、燃料槽和产出槽都当作开放端口。
- [ ] 端口可声明物品/液体过滤、容量、方向和自动化访问规则；手动交互、动物取物及机械运输由调用者身份与规则共同决定是否允许。
- [ ] 端口发现只依赖模块提供的能力，不扫描物品名称或写集中式类型分支；新容器和新搬运设备不得要求修改转移服务的核心流程。

### 2.2 转移正确性

- [ ] 由一个转移协调入口处理源与目标，复用现有库存和液体修改方法；不得由鸟、传送带或管道直接改槽位、`ItemData` 或液体字段。
- [ ] 预检不改变状态；提交在权威侧重新校验。容量不足时按实际可转移量提交，或按该端口声明的整批规则拒绝，不出现源已扣除而目标未收到。
- [ ] 为两端转移定义一次性计划与状态版本；提交时使用目标预留或等效的原子机制，任何一端失败都撤销本次变化。无法保证撤销或原子提交的自定义端口不能参与跨端口转移。
- [ ] 物品搬运保留实例数据、堆叠身份与附加状态；从库存取出时生成本次数量对应的数据，避免把仍在源槽中的可变 `ItemData` 引用直接交给目标。
- [ ] 液体搬运保留 `LiquidId`、实际份数及需要随液体转移的状态；不同液体不得因同一端口而自动混装。容量、精度和舍入沿用现有液体容器规则。
- [ ] 提交成功后通知真实所属库存/容器刷新，并沿用原有模块及区块存档链；失败或取消不产生物品或液体变化。容器位于背包中时也必须更新该背包的图标和状态。
- [ ] 处理源与目标相同、对象卸载或回池、跨区块、并发请求和联机权威；不得凭一次旧预检在后续帧直接扣取。

### 2.3 分层与依赖方向

以下是拟定的职责边界，具体名称在落地时与现有程序集边界核对：

```text
本体 / MOD 的 Item 定义与模块配置 → IContainerPortProvider → 类型化端口
本体 / MOD 的搬运者 → ContainerTransferService → 发现并使用两端的类型化端口
类型化端口 → 现有 Inventory_Data / Mod_WaterVessel / WorldLiquidSystem
存储提交 → 现有状态通知、存档与联机同步
```

- [ ] `IContainerPortProvider` 只负责枚举该实体的端口；端口 ID 在同一物品定义内稳定且唯一，不能依赖子物体顺序或 UI 槽位索引。一个实体可以同时有多个输入、输出端口。
- [ ] 以 `IItemTransferPort` / `ILiquidTransferPort` 分别定义最小读写契约；共同的请求/结果包含内容类型和单位，禁止通过强转或隐式换算把不同介质混用。新增可选能力使用新接口，不持续扩大基础接口。
- [ ] `ContainerTransferService` 拥有权限校验、重验、实际转移量、失败原因和提交顺序；端口实现只适配所属存储并报告能力。世界水源作为液体来源适配器接入，不伪装成容器物品。
- [ ] 将解析端口、校验请求、提交转移、发布结果拆成稳定的具名方法或事件边界，供 Harmony 等代码 MOD 扩展；结果观察者只读，不在通知中再次修改本次事务。
- [ ] 端口引用包含所有者稳定身份、运行态代际与端口 ID；回池、重载或世界切换后旧引用失效。端口发现和事务在权威侧工作，UI 仅展示结果。
- [ ] 端口发现限定在当前实体或已确定的邻接目标；可按运行态代际缓存并在模块结构变化时失效，不让大量传送带、管道每次工作都扫描全场景或反射所有模块。

## 3. MOD 扩展契约

### 3.1 内容型 MOD

- [ ] 本体与 MOD 共用端口配置结构和严格校验器。MOD 在已有 Item / Actor JSON 模块参数中声明所用端口类型、方向、过滤、容量与稳定端口 ID；继承和 Patch 后再校验最终定义，不另建只供 MOD 使用的第二套配置。
- [ ] 首批内置适配器覆盖库存和通用液体容器。内容型 MOD 可组合已有模块，定义新箱子、液罐和已注册的 `LiquidId`，无需增加核心代码或复制容器类。
- [ ] 配置引用的物品、液体、模块和端口类型必须存在；自定义类型 ID 使用 `modId:` 命名空间。重复端口 ID、错误方向、无效容量、未知字段和无效引用在目录发布前给出具体诊断，不能静默跳过。
- [ ] 配置只描述静态规则；端口库存内容、液体余量等运行态仍由所属模块独立持久化。读档先按当前定义重建端口配置，再恢复匹配稳定模块/端口身份的运行态，不用旧存档反写当前配置。

### 3.2 行为型 MOD 与注册

- [ ] 提供受限的 Lua 转移请求 API：查询端口、预览可转移量、请求转移、读取结果。Lua 只提出意图或提供无副作用的过滤规则；权限、实际扣取、回滚、通知和存档均由本体服务负责，不向 Lua 暴露原始 `Inventory_Data` 或世界液体写入。
- [ ] 现有 `ModItemApi.AddLiquid/RemoveLiquid` 继续按原用途兼容；新设备不得把这两个独立调用拼成一次跨容器转移，以免中途失败造成损失或复制。
- [ ] 如果需要超出已有适配器的原生端口算法，使用显式注册的端口工厂/策略及稳定类型 ID；注册返回可释放句柄。当前 MOD 包不能仅凭 JSON 或 AssetBundle 装入新的 C# 类，这类能力须先由本体或受支持的代码扩展提供；普通 MOD 仍可配置已注册类型。
- [ ] 端口工厂先供候选定义解析和校验，整份 MOD 内容通过后才随目录一并发布；重复 ID、依赖缺失或工厂异常使候选失败，不留下半注册端口。卸载、热重载失败、旧会话退役时释放注册句柄、订阅与缓存，不影响仍在运行的正式会话。

### 3.3 稳定性与权限

- [ ] 明确端口契约版本与配置迁移规则。已发布接口保持稳定；新增可选能力以独立接口或新版本接入，旧 MOD 不因基础接口增加成员而被迫全部改写。
- [ ] MOD ID、内容 ID、端口类型 ID 和端口实例 ID 各有固定用途；日志、存档和联机诊断记录可定位到所属 MOD 与端口，不按加载顺序生成持久身份。
- [ ] MOD 调用与本体调用使用相同的玩家背包访问规则、距离、方向、过滤、联机权威和事务校验；MOD 不能凭注册端口绕过玩家许可或跨世界访问。
- [ ] MOD 缺失或版本变化时遵循现有 MOD 存档与联机集合校验规则；未知端口或未知液体不能自动转为本体资源、清空内容或悄悄丢弃转移请求。

## 4. 现有容器接入

### 4.1 物品库存

- [ ] 为 `Mod_Inventory` / `Inventory_Data` 建立物品输入输出适配，沿用现有槽位限制、堆叠、重量/体积容量及库存事件。
- [ ] 首先让普通箱子通过端口接收和输出物品；验证满箱、可合并但无空槽、过滤拒绝和部分搬运。
- [ ] 玩家背包单独声明可被外部调用的范围和规则；主背包、快捷栏、手持、装备等不能仅因属于同一玩家就全部开放。

### 4.2 液体容器

- [ ] 为 `Mod_WaterVessel` 建立液体输入输出适配，复用现有 `AddLiquidAmount`、`RemoveLiquidAmount` 和容器间转移语义；瓦罐作为首个接入对象。
- [ ] 将水槽、储液罐实现为声明容量和接入规则的液体容器；若需要新的存储模块，仍实现同一液体端口，不复制瓦罐逻辑或按容器名称特判。
- [ ] 兼顾世界中运行的容器和背包内冷载荷的容器物品；只改真实拥有的那份状态，并通知所属库存。

## 5. 调用方接入顺序

### 5.1 鸟从玩家背包取种子

这里把需求中的“获取种植”按“取走种子”理解。

- [ ] 鸟在接近玩家并满足玩法条件后，查询玩家允许被取走的背包输出端口，按种子身份或标签筛选。
- [ ] 每次只通过统一转移入口取走实际可得数量；背包没有种子、目标无法接收、距离失效或权限不符时不扣物品。
- [ ] 鸟获得的种子进入它自身的承载状态或库存；取走后的行为、概率与冷却单独规划，不写进通用容器接口。

### 5.2 传送带向箱子送物品

- [ ] 传送带作为物品来源/搬运者，识别相邻箱子的物品输入端口，按端口方向、过滤与实际容量提交。
- [ ] 箱子拒收或满箱时，物品保留在传送带原位置；成功时只移除已进入箱子的数量。

### 5.3 管道向液体容器送液体

- [ ] 管道的输出端连接瓦罐、水槽或储液罐的液体输入端口；连接方向、类型、容量和传输速率由设备层处理。
- [ ] 目标不接受该 `LiquidId` 或容量不足时，液体留在来源；禁止以物品堆叠或世界液深直接表示管道内的容器份数。

### 5.4 抽水器从世界水源取液体

- [ ] 用 `WorldLiquidSourceResolver` 确认世界格液体身份与剩余液深；最终抽取必须走 `WorldLiquidSystem.TryPump`，不得改 Ground 或从水地块名称推断液体。
- [ ] 定义世界液深与容器液体份数的显式换算、精度和每次抽取上限；先确认目标能接收，再在一次可靠提交中完成抽水与入罐，避免抽走世界水却未入罐。
- [ ] 抽水器可接瓦罐或储液罐；无水、源格卸载、目标满、液体不匹配、无动力时不产生液体。设备配方、动力和操作面板另行规划。

## 6. 首批实现与游戏内验收

- [ ] 先落地端口契约、转移协调入口、共用 MOD 配置校验，以及普通箱子和瓦罐的适配；确认现有手动库存操作和液体容器交互仍正常。
- [ ] 再接入玩家背包与鸟、传送带与箱子、管道与容器、世界水源与抽水器；每个调用方只通过端口通信。
- [ ] 在真实 Play Mode 中观察四条完整转移链的源、目标、UI 与存档状态；分别覆盖满容器、类型拒绝、部分转移、重复触发、卸载重进和保存重进，确认总量守恒。
- [ ] 联机环境下确认只有状态权威方提交转移，客户端不会重复扣取或生成内容。
- [ ] 在真实 Play Mode 中分别使用仅配置 JSON 的 MOD 箱子、使用 MOD 液体的容器、通过 Lua 请求转移的设备，观察过滤、容量、守恒、存档重进与联机结果；新增内容不修改转移服务或现有调用方。
- [ ] 真实运行中核查重复端口 ID、缺失依赖、热重载失败和 MOD 卸载：给出可定位诊断，正式世界的旧注册不被候选污染，卸载后没有残留端口或回调。

## 7. 后续待规划

- 玩家背包允许鸟取走的具体槽位、种子筛选、偷取概率与反制方式。
- 水槽、储液罐和管道的容量、连接位置、速率，以及是否允许多种液体混合。
- 世界液深与液体份数的换算比例；抽水器的动力消耗和取水范围。
- 跨区块长距离物流的暂停、恢复与持续模拟规则。
