# FlatWorld 大地图分区存档与按需加载待办

## 1. 系统定位

让玩家进入大型世界时只读取核心存档和当前位置附近的区块记录。远处的区块修改留在磁盘；玩家移动时提前读取将要进入的区块，数据就绪后再恢复地形、建筑和自然物，最后绑定表现。

当前地形已经按玩家位置生成和逐出，但 `SaveDataMgr.LoadSaveByDisk` 会同步读取整个 `.bytes` 文件，并把 `CompactSaveEnvelope.ChunkRecords` 全部反序列化到 `chunkDeltas`。新格式确定为每个存档一个文件夹；本改造针对磁盘存档和内存占用，不改变程序化地形生成、世界种子或现有 ChunkView 表现规则。

```
启动：核心存档 + 区域目录 → 玩家附近区块的磁盘记录 → 生成基线 → 覆盖差量 → 表现
移动：视野外一圈提前预读 → 进入显示窗口时使用已读数据恢复并绑定 → 远离区块保存脏数据、释放租约和缓存
```

## 2. 存档结构

### 2.1 核心存档

- 每个存档使用独立文件夹，以安全的存档 ID 定位；玩家可见名称仍由核心元数据保存。目录布局示意如下，具体扩展名由实现时确定：

  ```text
  LocalSaveData/
    <save-id>/
      manifest.bytes
      regions/
        <world-key>/
          <region-x>_<region-y>.region
  ```

- `manifest.bytes` 保留玩家、星球、世界时间、MOD 元数据、全局系统快照及区域文件目录等核心数据。
- 核心存档只保存区块区域目录及版本，不再内嵌所有 `ChunkSaveRecord`。
- 新格式允许重构 `GameSaveData` 和 MemoryPack 存档布局，不为旧单文件存档保留兼容字段；玩家与世界级数据、区域目录和区块载荷仍按职责分开。
- Seed 只还原区块的初始生成基线。地块、液体、自然物、玩家放置物及其模块等状态，只要发生变化且重进世界后应保留，就写入所属 Chunk 的差量记录；确实可由 Seed 和世界时间准确重算的状态不重复保存。
- 没有持久变化的区块不写磁盘记录，进入时按生成基线重建；即使大量区块都有变化，也只把玩家附近的区块记录加载到内存。
- 不再保留独立的 `EcologyWorldSaveData.Chunks` 区块状态容器。自然生成的树等 Item 与其他 Item 共用所属 Chunk 的状态覆盖和删除记录；生态规则与冻结生成配置仍留在核心存档。
- 机械网络、掉落物等其他世界级载荷要审计其增长和权威边界；不能只移走 `ChunkRecords` 就宣称大地图内存有界。

### 2.2 区域文件与索引

- 按维度世界键和区块坐标划分区域；区域目录只定位磁盘文件，不把区域内所有区块反序列化到内存。
- MemoryPack 只负责选定数据对象的序列化与反序列化；存档目录、文件路径、区域索引和随机读取由独立存储层管理，不把文件夹当作 MemoryPack 对象。
- 读取流程为：玩家窗口给出 Chunk 地址 → 由坐标计算区域地址 → 用核心目录定位区域文件 → 读取该区域的 Chunk 索引 → 按偏移与长度读取单个 Chunk 载荷 → MemoryPack 只反序列化该 `ChunkSaveRecord`。
- 每条区块记录保留 `ChunkSaveRecord` 的稳定数据语义，包括地块、液体、农业、污染、支撑层、Item／模块状态、建筑、AI 和未知 MOD 数据。
- 自然生成的 Item 使用稳定 GUID 对齐生成基线；生长进度、损伤、库存等变化按普通 Item 状态保存，采集或销毁用删除标记保存，必要的自然补位时间跟随该删除状态保存。恢复时先生成基线，再应用状态覆盖和删除标记，同一 GUID 不得重复实例化或回退到初始状态。
- 地块与 Item 等需要在区块卸载期间继续随时间变化的状态，保存必要的当前状态和上次结算游戏时间；重新加载时按其规则补算，不能仅靠 Seed 把它们重置为初始状态。
- 区域文件提供按区块地址查找的偏移、长度与校验信息；读取单个区块时只读取它的字节段。不能直接对完整区域文件调用普通 `MemoryPackSerializer.DeserializeAsync(Stream)`，因为该接口会先读到流末尾再反序列化。
- 当前项目的有限拓扑为 `WorldTopologyMode.Wrapped`。先按 `WorldTopologyBounds` 归一化 Chunk 原点，再计算磁盘 Region 键；跨世界接缝的两个坐标必须命中同一份权威区块记录。
- 选区域边长时计算有限世界各轴的 Chunk 数及预计区域文件数量。区域边长不必强制整除世界边长；边缘不足一整区时只保存有效 Chunk，接缝外的预读回绕到另一侧并去重。
- 无限世界的负坐标用向下取整求 Region 坐标；区域边长写入存档元数据，读取时按存档内数值寻址，不能用当前默认值重新计算已保存 Chunk 的文件归属。
- 启动时读取核心目录，不遍历全部区域文件或建立所有 Chunk 对象；核心目录指出某区域存在记录时，该区域文件缺失或损坏必须报错，不能按未修改的新区块处理。
- 区域大小、玩家可调的预读圈数与缓存预算在目标设备实测后确定；首版必须有明确上限，不能随着探索总面积无限增长。
- 存档路径必须继续位于 `Application.persistentDataPath/Saves/LocalSaveData/`；文件名和路径应由存档 ID、世界键及整数区域坐标稳定推导，并阻止路径穿越。

### 2.3 保存事务与格式边界

- 保存时先写新版本的区域数据，再提交引用这些区域文件的核心存档；核心提交前，旧区域文件保持可读。失败时旧正式存档仍是一套完整世界。
- 离开窗口的脏区块先写入本次会话的临时区域数据，再释放内存；临时数据只有在核心存档成功提交后才成为正式存档的一部分。崩溃恢复不能把未提交的临时数据误认为已保存进度。
- 自动保存、手动保存和退出保存继续按修订号防止旧任务覆盖新状态；后台只处理不可变快照，不读取 Unity 对象。
- 保留当前正式存档、备份和临时文件的恢复语义，并扩展到整个存档文件夹。清理过期区域文件只能发生在新核心存档和备份都不再引用它们之后。
- 新格式使用独立格式头与版本，在反序列化区块载荷前校验。旧单文件存档明确提示不支持；实现时不新增旧格式迁移、兼容读取或旧格式写入逻辑。读取失败不能自动删除或覆盖原文件。

## 3. 运行时流送

### 3.1 预读与发布

- 单机以本地玩家的相机区块窗口为依据；联机主机以所有玩家观察者窗口的并集为依据。
- 以当前显示区块窗口为边界，默认向 X/Y 各外扩一个 Chunk；玩家可调整向外预读的圈数。预读目标始终是“外扩窗口减去显示窗口”，显示窗口已包含的相机缓冲不得重复计算。
- 预读圈数和预读缓存容量分开设置：圈数决定提前覆盖多远，容量决定未进入视野的数据最多占用多少内存。玩家调大时可用更多内存换取较高的预读命中机会，但实际圈数仍受目标设备安全上限约束。
- 外圈预读同时包含程序化区块数据与磁盘里的存档差量；玩家进入显示窗口时应优先复用已完成的数据，而不是届时才开始读磁盘。
- 外圈预读在玩家仍位于原窗口时就启动，并与可见区块工作并行；可见区块优先，但不能以“所有可见区块和表现都已完成”为启动条件。为预读保留受限的读取并发，避免它挤占可见区块。
- 配置范围内各方向均可预读，不按移动方向猜测。预读后没有进入视野的区块允许留在有上限的缓存中，并按普通缓存逐出规则释放。
- 位置变化后取消已经过时且未开始的请求，并重新排序仍有效的请求；已经完成的未使用结果可作为缓存保留。
- 磁盘读取、校验和纯数据反序列化在后台完成；Unity 对象访问、权威地形恢复和 ChunkView 绑定留在主线程。
- 同一区块的并发请求合并；携带世界纪元和窗口版本，避免旧世界或旧位置的完成结果覆盖当前世界。
- 读取失败、MOD 定义缺失或数据损坏必须明确报错，不能把原有改动当作空区块覆盖保存。

### 3.2 缓存与逐出

- 缓存至少区分可见、预读、被系统租用、脏数据和可逐出状态；脏数据安全写入会话临时区域前不得逐出唯一副本。
- 预读缓存同时限制区块数量和估算字节数；超过玩家设置的预算时优先逐出最远且无租约的干净记录。可见区块、系统租用区块和未安全落盘的脏数据不能为了满足预读预算被误删；预读预算不等于游戏总内存上限。
- 调低圈数或缓存预算时，取消尚未开始的多余预读并逐步释放超预算缓存；调高时按新窗口立即排队，不等待玩家再次跨 Chunk。
- 世界切换、存档切换、传送、死亡重生和退出时取消旧请求，等待或安全终止相关写盘任务，释放旧缓存。
- 机械整网、掉落物和其他跨区块全局状态继续由各自权威存档管理，不能因视觉区块逐出而拆散状态。

## 4. 实施清单

- [ ] 确认所有 `chunkDeltas`、自然物状态与删除记录的读写入口，以及联机快照对“全量区块常驻”的依赖。
- [ ] 将现有 `EcologyWorldSaveData.Chunks` 中的 Item 状态、删除 GUID 和自然补位时间并入普通 Chunk 的 Item 差量；移除旧生态区块状态的生产、读取和双写路径，保留生态规则与冻结生成配置。
- [ ] 新格式直接替代当前 `.bytes` 单文件的读取和写入入口；不新增旧格式迁移或兼容解析，旧档在存档列表中明确显示为不支持，避免误当成空存档覆盖。
- [ ] 定义每存档一个文件夹的布局、核心封装、区域目录、区块索引、版本与校验规则；玩家可见存档名与安全目录 ID 分开。
- [ ] 实现只读取指定区块记录的磁盘存储层，以及可取消的后台预读。
- [ ] 把可配置圈数的视野外地形及存档差量预读接入现有 `ChunkMgr` 窗口；默认一圈，预读必须在区块进入视野前并行开始，恢复差量完成后再实例化 Item、建筑、AI 和表现。
- [ ] 提供玩家可调的预读圈数和预读缓存容量，显示设置的内存代价及实际生效值；范围和默认值以目标设备实测确定。
- [ ] 实现有上限的记录缓存、脏数据追踪与安全逐出。
- [ ] 改造自动、手动、退出保存为区域数据与核心存档的一致提交；保护备份与旧任务修订号。
- [ ] 改造存档列表、删除、复制、备份、联机快照及世界切换流程，使它们以整个存档文件夹为单位处理。
- [ ] 审计机械网络、掉落物等世界级载荷；对仍随探索无限增长的数据另设可持续的存储边界。
- [ ] 使用隔离存档在真实 Play Mode 覆盖新建世界、跨区域往返、大量修改、树及其他 Item 成长、地块随时间变化、自然物采集与补位、保存重进、强制退出恢复、维度切换和联机多观察者。
- [ ] 在目标设备以不同圈数和缓存容量测量大存档的进入时间、峰值内存、移动预读命中率和最慢区块出画时间；结果达到预设预算后再勾选验收。

## 5. 后续待规划

- 综合有限世界 Chunk 数、预计区域文件数量、单区索引大小、写入放大与目标设备 I/O，确定区域边长；再确定预读圈数与缓存容量的各平台默认值和可调范围，以及预读读取并发的上限。
