## 1. 系统定位

玩家、AI 动物、树木、石头、矿物、其他世界道具及手持物，共用一套 ECS 玩法架构。首要目标是通用能力只维护一次，新增功能不再分别补“玩家 GameObject 版”和“动物 ECS 版”；批量计算、批量渲染与自由接管是这套架构带来的能力。项目处于开发期，不保留旧版本兼容路径。

## 2. 模块与权威边界

- 复用 `WorldEntityRuntime`，按世界/维度管理实体；不按玩家、AI、静物、手持形态另建平行 ECS 世界。共用 World 不等于迁移完成，必须共用能力数据与执行规则。
- 生命、伤害、体力、营养、Buff、库存、装备、生长、生产、采集等按需组合；系统按组件查询执行，不按物种名或 `Player` 类型特判。新增内容优先组合配置，新机制才增加可复用能力。
- AI 动物只是额外组合感知与自主决策的实体。拆开“营养与进食”和“AI 觅食”、“飞行能力”和“自动起飞决策”；玩家完整营养、濒死等机制不能被当前 AI 简化实现替代。
- **删除“远处 ECS、近处完整 Item 接管玩法”的升降级方案。远近始终由 ECS 持有唯一玩法状态，不保留第二套 Module Tick 或静默回退。** 未迁移能力必须明确列出，不能忽略后声称完成。
- GameObject 仅保留必要的输入、摄像机、UI、音效及物理/表现接口适配；只提交命令、读取结果，不保存另一份生命、位置或库存权威。物理反馈统一进入运动结算，不允许双向抢写位置。
- 主体、阴影和手持表现接入 BRG/共享批量绘制。静物按事件或低频更新，无变化不重传实例；连续移动和操作保留响应频率。Job 按读写依赖并行，不要求所有模块同时执行。

## 3. 玩家与控制来源

**明确目标：将 `PlayerControl` 模块换成 `AI Brain` 模块，同一身体就由 AI 控制；将 `AI Brain` 换成绑定玩家会话的 `PlayerControl`，玩家就能直接附身该实体。只替换控制来源，不创建“玩家版动物”或更换玩法后端。**

```text
同一实体 + 共享能力 + PlayerControl = 玩家控制
同一实体 + 共享能力 + AI Brain      = AI 控制
PlayerControl / AI Brain → 唯一控制权仲裁 → 统一动作意图 → 共享 ECS 能力
```

两个控制模块只负责产生动作意图，移动、攻击、进食等执行能力不得依赖特定控制源。同一实体每个模拟步只能有一个有效控制源；切换只修改控制模块与绑定，不能暂停整个实体或重建能力集合。所需输入、感知等依赖在装配时明确校验。

玩家会话、档案与控制身体分离。绑定控制器即可接管具备相应能力的动物，解除后可交回 AI；不重生、不换实体身份，不重置血量、Buff、冷却、库存、阵营或蜂巢归属。只暂停自主决策，生存与受伤照常运行；控制器不会凭空添加飞行、库存或持握能力。

接管在模拟边界统一交接，清理旧输入与导航意图；攻击遵守统一取消规则，不能借切换刷新冷却。镜头、UI、交互、区块加载及环世界局部投影跟随当前控制实体，而非固定依赖原 `Player` 对象。

## 4. MOD 实体模块扩展契约

统一 ECS 不等于封闭 ECS。正式 MOD 架构必须允许作者直接给统一实体增加自定义玩法模块，而不是要求 MOD 为实体重新创建一套 `Item + GameObject + MonoBehaviour` 权威后端。

```text
ECS Entity（唯一玩法实体）
    ├─ 官方原生模块：IComponentData + Burst System
    ├─ MOD C# 模块：Managed Entity Module
    └─ 可选 GameObject Proxy：UnityEngine / 物理 / 特效 / 特殊表现
```

- 提供稳定的 `EntityModuleRegistry`。MOD C# 可使用 `modId:moduleId` 注册自定义实体模块，并将模块挂到玩家、动物、植物、建筑、道具等任意满足依赖的实体上。
- MOD 模块可以通过公开的 Entity API / EntityHandle 查询并修改允许暴露的 ECS 能力数据；常用玩法优先提供稳定的 `Hook / Rule / Command`，例如伤害前后、治疗、移动、攻击、交互、Buff、属性修正、生成与死亡。
- 类似“无敌”模块应能注册统一伤害规则：模块挂载后，在伤害结算前拒绝伤害；不要求为玩家、动物、树木分别实现，只要目标共用统一生命/伤害契约即可复用。
- MOD Managed C# 模块可以实现任意托管逻辑，但默认不等于一个 GameObject，也不要求继承 `MonoBehaviour`。只有确实需要 `Transform / Collider / ParticleSystem / AudioSource` 等 UnityEngine 能力时，才申请 GameObject Proxy。
- GameObject / MonoBehaviour MOD 与 ECS 之间提供稳定 Bridge Contract，沿用 `DamageSender → DamageContext → ECS Settlement` 这种模式扩展交互、Buff、移动、库存、音效与 VFX；跨边界优先传标准数据、命令与结果。
- 可提供受控的高级 Entity API 给高级 C# MOD 直接操作公开 ECS 数据，但不能让 MOD 绕过生命周期、存档、联机权限与世界归属规则随意持有失效 Entity 引用。
- **不承诺运行时动态新增任意 Burst `IComponentData / ISystem / IJobEntity`。** Windows Mono 下允许运行时加载托管 C# MOD；官方高频模块继续使用预编译 Burst ECS，MOD 自定义逻辑通过 Managed Module 与标准扩展点接入同一个 Entity。
- MOD 模块 ID、状态与依赖必须可序列化；联机时由权威端执行会改变玩法结果的模块逻辑，并纳入现有 MOD 集合/内容一致性校验，避免客户端各自结算。
- 现有 `ItemManager + Item + Module` 在迁移期可以继续作为兼容入口，但最终不作为世界实体的第二套权威运行时。旧 MOD 能力应逐步迁移到 `Entity Module API + Managed C# Module + GameObject Bridge`。

新增一个通用能力，玩家与动物直接组合复用，无需另写 GameObject 版本。MOD 作者可注册一个 Managed C# Entity Module 并挂到任意满足契约的实体；例如同一个“无敌模块”挂到玩家、动物或建筑后，都由统一伤害链拒绝伤害，不需要复制目标类型专用实现，也不强制创建 GameObject。仅替换控制模块，让同一只动物完成“AI 活动 → 玩家接管 → 行动并受伤 → 交回 AI”，也让原玩家身体在满足依赖后换上 `AI Brain` 自主行动；身份和状态连续，无双控制源抢写，也不换模型假装附身。远近切换始终不改变玩法后端。快速切槽、消耗最后一件、保存重进、F5、区块往返与跨维度后，无重复扣减、重复掉落、状态丢失或旧回调误操作。
