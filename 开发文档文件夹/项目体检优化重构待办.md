## 2. 存档可靠性与存档架构

### H01 · P1 · 保存失败时中止手动退出

**现状与影响：** `SaveToDisk` 会返回失败，但 `SaveCurrentToDisk` 和退出保存入口没有把结果传回上层。退出协程在保存之前已经修改世界状态并触发退出事件，随后继续释放系统和场景。手动退出的控制流缺口仍待修复；实际写盘失败后的游戏表现尚未复现。

**F5 当前边界：** 世界内资源更新已改为候选目录加载、校验与同帧发布，不调用保存、退出或重新进入存档。失败保留旧目录，活跃玩家和区块保持原实例；旧代资源在正式退出后回收。现有实例只更新兼容的显式模块参数及外观，模块组合和外壳结构由后续新实例应用。联机、在用 Bundle 替换、删除既有身份或改变液体编号不支持原位更新。本轮后续实机回归按用户要求跳过，H01 不因此整体标记完成。

**代码入口：** [SaveDataMgr.cs](<C:/Users/CatStudio/Desktop/TerraFlat-master/Assets/5_Scripts/5-3_GamePlay/Core/Save/SaveDataMgr.cs>) 中的 `Save_And_WriteToDiskAndRecordExitTime`、`SaveCurrentToDisk`、`SaveToDisk`；[GameManager.cs](<C:/Users/CatStudio/Desktop/TerraFlat-master/Assets/5_Scripts/5-3_GamePlay/Core/Lifecycle/GameManager.cs>) 中的 `BackToHelloScene_Coroutine`。F5 独立入口位于 [GameRes.HotReload.cs](<C:/Users/CatStudio/Desktop/TerraFlat-master/Assets/5_Scripts/5-3_GamePlay/Core/Lifecycle/GameRes.HotReload.cs>) 的 `ReloadResourcesInPlace`。

**建议流程：** 准备退出 → 捕获完整状态 → 成功提交存档 → 发布退出结果并释放世界。失败分支保留可恢复的世界状态，允许重试。

- [ ] 让手动保存与退出调用方获得明确的保存结果；梳理保存前事件订阅者，避免提前销毁需要保存或恢复的数据。
- [ ] 保存失败时停止退出后续步骤，并提供明确反馈与重试路径；保留已有临时文件、备份、原子替换和写入版本保护。
- [ ] 在隔离存档中完成成功保存、可控写盘失败和重试的真实验收，确认失败不丢失当前世界，成功后背包、建筑、液体、掉落物与机械状态可恢复。

**完成条件：** 手动退出、F5 重载和自动保存交错执行时均有确定结果；较早的后台任务不能覆盖较新的存档。故障注入仅使用隔离目标，不破坏正式存档。

## 3. 联机权威与同步开销

### H02 · P1 · 收紧客户端物品状态提交权限

**现状与影响：** `OnServerStateSubmit` 检查连接身份、负载大小、目标是否可同步及版本后应用客户端快照，但该入口缺少发送者对目标的操作权限、交互距离及具体玩法语义校验。反序列化路径会合并物品公开字段和模块状态。版本号只能处理状态先后关系，不能替代业务授权。

这里涉及该路径允许同步的世界物品等对象；它排除了 Player、Map 和 InHand，不能据此声称客户端能通过此入口任意修改玩家数据。

**代码入口：** [NetworkItemStateCoordinator.cs](<C:/Users/CatStudio/Desktop/TerraFlat-master/Assets/5_Scripts/5-4_Networking/Gameplay/NetworkItemStateCoordinator.cs>) 中的 `OnServerStateSubmit`、`ShouldSynchronize`、`CanSynchronize`；[ItemNetworkStateSerialization.cs](<C:/Users/CatStudio/Desktop/TerraFlat-master/Assets/5_Scripts/5-3_GamePlay/Entities/Item/Networking/ItemNetworkStateSerialization.cs>) 中的 `Apply`、`TryMergeSnapshot`、`CopySerializableFields`。

- [ ] 列出客户端可提交的合法操作及每类操作的服务端校验规则，明确哪些数据仅允许服务端写入。
- [ ] 优先让客户端提交拾取、使用、攻击等操作请求，由服务端验证并计算结果，再广播权威状态；现有建筑事务可作为项目内参考。
- [ ] 使用隔离 Host / Client 验证合法交互，并验证伪造目标状态、越界操作、资源不足及重复请求均不会造成越权修改或重复结算。

**完成条件：** 请求与目标对象的权限关系有明确规则；双端状态一致；旧版本 / 重复请求及断线过程不会绕过校验。尚未完成双端复现，具体可利用范围需实测确认。

**参考：** [Mirror：客户端输入验证与服务端权威](https://mirror-networking.gitbook.io/docs/security/cheating)。该资料支持校验原则，项目是否满足原则仍以上述代码和实测为准。

### H06 · P2 · 测量并优化网络状态扫描与序列化

**现状与影响：** 同步协程会生成运行时物品快照，并对轮询到的对象捕获、序列化和计算状态哈希。每帧扫描上限会影响兜底扫描的周转时间。项目已存在 `OnRuntimeStateChanged` 事件链，因此不能把所有状态更新都视为依赖轮询。

**代码入口：** 上述 `NetworkItemStateCoordinator.cs` 的 `SnapshotRuntimeItems`、`ProcessServerItem`、`OnRuntimeStateChanged` 及运行时事件订阅位置。

- [ ] 在不同实体数量的真实联机场景记录序列化耗时、GC 分配、每轮扫描时间和状态传播延迟。
- [ ] 结合 H02 的最终协议，优先补齐有效状态变化的事件覆盖，评估脏队列或模块版本号，并保留必要的低频兜底检查。
- [ ] 只对测得的热点减少临时分配或缓存序列化结果，验证容器内容、模块状态及对象生命周期变化不会漏同步。

**完成条件：** 有同场景优化前后数据，既降低开销又保持同步完整性；不得只以减少扫描次数判断优化成功。

**参考：** [Unity 2022.3：GC 与临时分配优化](https://docs.unity3d.com/2022.3/Documentation/Manual/performance-garbage-collection-best-practices.html)。
