### 0.2 已确定的版本顺序

**先完善单机，双人另列后续验收。季节长度可自由调整，默认每季 6 天、一年 24 天。** 单机开发继续使用已有世界权威边界，避免将来为双人重写；当前不要求每一项策划都先跑通双实例。

```text
首夜求生：采集 → 石器 → 取火 → 食物与基础饮水
→ 稳定基地：储存 → 制作 → 冶炼 → 首件金属工具 → 可重复种植
→ 季节准备：陶器与储水 → 夏季水盐 → 秋季储粮 → 冬季与药材
→ 探索回报：准备补给 → 发现遗迹 → 带回资源 → 改善基地
→ 单机阶段人工验收
→ 双人基地、遗迹和恢复验收
→ 高级工业、后期医药与太空
```

以上表示开发依赖，玩家可并行发展。陶器不要求青铜镐，草药不要求探索遗迹，铁器与青铜不互相强制解锁；新手引导允许提前完成和自动跳步。

遗迹服务于加速、补给和长期线索，不能成为获得铁矿、锡矿、黏土、盐或首份种子的唯一来源。资源不足时应有可理解的替代获取路径，不能靠管理员赠送补救。

### 0.5 系统边界与验收规则

- 配方以启用的 JSON 目录为真源；普通制作没有现成的独立工作站限定字段，策划要求“只在工作台制作”时须单列工作站能力需求，不能当作改配方名称就能完成。
- 教程负责进度，自言自语负责表达；普通提示不暂停、不锁输入，紧急生存反馈优先，角色不透露尚未发现的地点。
- 世界时钟负责时间，天气负责降水，植物与玩家模块各结算自身状态；雪覆盖与平台支撑各自保存，渲染层只负责显示。
- 地形、建筑、库存和进度分别遵循已有权威与存储边界；失败不能出现扣了材料却没有产物，或清掉建筑却丢失库存。
- **当前项目不兼容旧存档。** 只要求同版本保存恢复；结构版本不兼容时明确报错并停止加载，不追加旧字段回退或迁移，不覆盖原档。
- 代码实现时按用户要求做静态检查与 MCP 控制台检查；实际单机、双人、数值和性能测试由用户执行，未经要求不主动运行测试。
- 内容校验保留手动统一入口，不因七月“构建前校验”的表述重新添加自动构建阻断。
- 阶段完成依据是可玩的完整流程与人工结果；脚本存在、静态通过、控制台无错误分别记录，不能代替玩法验收。

### 0.6 策划验收问题

每项机制都需要写清：获取入口、加工或交互步骤、成本、收益、失败原因、补救方式、玩家反馈、保存内容和人工验收场景。只有方向的远期内容明确写成候选，尚未答复的选择不擅自定稿。

本轮实现优先连接三类断点：第一件金属工具之后不知道做什么；季节压力来临之前没有准备路径；探索带回的东西没有用途。

## 1. 产品定位

建议将 FlatWorld 的核心定位收束为：

> **支持 1～2 人游玩的持续世界生存沙盒。玩家从荒野求生开始，建立基地，发展农业和冶炼工业，探索遗迹，并最终获得离开星球的技术。**

该定位能够自然容纳项目已有的：

- 程序化世界与 Chunk 流送
- 长期存档
- 组合式 Item/Module 架构
- 生存、食物、温度和天气
- 制作、建造、农业和冶炼
- 战斗、AI 和动态导航
- 双人联机
- 火箭、太空与星球迁移

当前项目的主要问题不是缺少系统，而是：

1. 系统数量较多，但缺少统一的成长主轴。
2. 世界生成能力强，但探索地点和差异化奖励不足。
3. 生存维度较多，但成熟度和重要性不一致。
4. 配方、Prefab、GUID 和字符串 ID 容易发生内容断链。
5. 单机、联机和太空同时扩张，存在范围失控风险。

## 4. 纵向切片：“第一块铁”

建议把首个完整版本的目标定义为：

```text
解决食物与饮水
→ 制作石器
→ 熬过第一夜
→ 建立帐篷、箱子和工作台
→ 找到矿物或遗迹线索
→ 建造熔炉
→ 获得第一块粗铁锭
→ 解锁下一阶段目标
```

目标体验时长建议为 **60～90 分钟**。

### 阶段划分

1. **落地求生**：认识移动、拾取、背包、饥饿和饮水。
2. **夜晚准备**：制作基础工具、取火工具和火堆。
3. **建立据点**：建造帐篷、箱子和工作台。
4. **进入金属时代**：寻找铁矿、准备燃料、使用熔炉。
5. **长期诱因**：通过遗迹、蓝图或特殊部件提示更远目标。

### 验收标准

- 新玩家无需外部攻略即可点燃火堆。
- 玩家能够解释工作台和熔炉的用途。
- 玩家知道死亡原因和改进方式。
- 出生区域不存在关键资源断档。
- 第一块铁出现后立即产生一个明确的新目标。
- 失败主要来自玩家决策，而不是资源随机性或系统信息缺失。

## 5. 自言自语系统设计

已确定使用**玩家控制角色的自言自语**承担世界内引导，而不是传统任务列表。

### 设计原则

- 角色表达观察、需求和计划，不朗读系统命令。
- 系统只在必要时显示按键等操作提示。
- 自言自语不暂停游戏，也不锁定玩家操作。
- 紧急生存反馈优先于教程和氛围台词。
- 角色不能知道其尚未接触过的信息。
- 自言自语不能代替生命、寒冷、中毒等关键 UI 警告。

示例：

不推荐：

> 按 B 键打开制作面板，然后制作石斧。

推荐：

> 这些材料应该能做把石斧。

旁边可以单独显示较弱的系统提示：

```text
[打开制作面板]
```

### 当前运行链

```text
ICharacterSpeechContextContributor
→ CharacterSpeechContext.Facts
→ ConfiguredSpeechProvider
→ Resources/Dialogue/Soliloquy/*.json
→ CharacterSpeechRequest
→ CharacterSoliloquyController
→ ScreenSpaceSpeechBubblePresenter
```

### 当前配置位置

```text
Assets/Resources/Dialogue/Soliloquy/
```

现有饥饿配置：

```text
Assets/Resources/Dialogue/Soliloquy/need_hunger.json
```

### JSON 配置方向

JSON 是自言自语内容、条件、优先级、显示时间、冷却和一次性标记的唯一配置来源。

支持的结构化条件操作符：

```text
Equal
NotEqual
Greater
GreaterOrEqual
Less
LessOrEqual
Exists
NotExists
```

不允许在 JSON 中执行任意 C#、脚本或自由表达式。

### 台词优先级

1. `Emergency`：濒死、严重饥饿等紧急状态。
2. `Critical`：正在恶化的危险状态。
3. `Need`：教程目标、普通生存需求。
4. `Ambient`：天气、环境和氛围感想。

### 教程设计边界

- 不实现传统任务面板。
- 不暂停游戏或强制锁定输入。
- 不生成教程专用资源。
- 不自动赠送材料。
- 允许玩家提前完成目标并自动跳步。
- 教程状态机负责进度，自言自语系统只负责表达。
- 教程进度与台词播放完成标记分开保存。

## 8. 当前系统优化优先级

新手教程暂不继续扩展后，建议按以下优先级优化系统。

## P0：优先处理

### 8.1 生物生成与生态预算系统

这是当前最推荐立即开发的模块。

#### 当前问题

- 基础生成表同时包含鸡、野猪和狼。
- 狼另有独立生成配置，可能重复投放。
- 基础生成权重总和超过 1，但当前实现按顺序累加判断，不是真正的归一化权重。
- 缺少按物种、区域和玩家周边限制的存活数量预算。
- 时间触发依赖狭窄容差窗口，时间跳跃可能漏掉生成。
- 缺少远距离休眠、回收和生态恢复规则。

#### 优化目标

```text
动物生成组
敌对生物生成组
夜间生物生成组
特殊里程碑生物生成组
```

增加：

- 权重归一化。
- 全局种群上限。
- 单物种上限。
- 玩家周边上限。
- 生物群系过滤。
- 昼夜和光照过滤。
- 火堆安全范围。
- 时间跨越补偿。
- 远距离休眠或回收。
- 死亡后的生态补位。

#### 验收标准

- 连续运行多个游戏日不会无限堆积生物。
- 实际生成分布符合配置权重。
- 睡觉或时间跳跃不会漏刷或重复刷。
- 敌人不会在玩家视野或已点燃火堆旁出现。
- 保存重载后不会重复处理已完成周期。

主要入口：

```text
Assets/5_Scripts/5-3_GamePlay/Manager/MonsterSpawnerManager.cs
Assets/5_Scripts/5-3_GamePlay/Spawner/SpawnerConfig.cs
Assets/Resources/Config/SpawnerConfig.asset
Assets/Resources/Config/SpawnerConfig_Wolves.asset
Assets/Resources/Config/SpawnerConfig_Ghost.asset
```

### 8.2 制作系统公共核心重构

当前四套制作入口存在大量重复逻辑：

```text
Mod_HandMade
Mod_HandCraftTable
Mod_MakeTable
Inventory_WorkBench
```

建议抽取统一核心：

```text
CraftingRecipeMatcher
CraftingTransaction
CraftingResult
CraftingService
```

统一处理：

- 配方匹配。
- 镜像配方。
- 输入数量校验。
- 输出空间预检查。
- 材料扣除。
- 产物添加。
- 制作成功事件。
- 单机与联机事务边界。

#### 验收标准

- 四种制作入口使用同一个制作事务。
- 失败制作不消耗材料。
- 空间不足时不发生部分产出。
- 多输出配方保持数量守恒。
- 单机和联机结果一致。
- 清除 `Mod_HandMade.GetDefaultTargetInventory()` 的未实现异常。

> 由于新手教程 Agent 可能正在修改制作成功事件，建议等教程改动合并后再开始此重构。

### 8.3 内容配置校验系统

需要建立一个统一编辑器检查入口，覆盖：

- 配方输入和输出 ID。
- 建筑召唤器和世界建筑关系。
- Spawner 生物 ID、权重和重复配置。
- 战利品表 ID。
- 生物群系生成物。
- 固定 Resources 路径。
- 重复物品 ID。
- 必填模块和 Prefab 引用。
- 物品显示名与描述污染。

校验器应只报告问题，不应未经确认自动修改资产。

#### 验收标准

- 一个菜单命令检查全部本体内容。
- 错误包含资源路径、字段名和错误 ID。
- 正式构建前不存在缺失引用和重复 ID。
- 配置错误在编辑阶段被发现，而不是进入运行时才暴露。

## P1：核心系统完善

### 8.4 自动天气循环

当前天气支持设置晴、雨和强度，但正式自动调度不足。

第一版建议只实现：

```text
晴
阴
雨
```

运行逻辑：

```text
根据星球/生物群系计算候选权重
→ 选择天气
→ 持续一段时间
→ 平滑过渡
→ 保存天气和剩余时间
```

验收重点：

- 天气不会频繁跳变。
- 保存重载后天气状态一致。
- 雨效、温度和植物生长使用同一权威天气。
- 自动测试可以注入固定天气。

---

### 8.5 农业和植物成长统一

当前存在：

```text
Mod_Seed
Mod_Grow
Mod_PlantGrow
```

需要明确唯一农业主链：

```text
种子
→ 耕地种植
→ 环境倍率
→ 成长阶段
→ 成熟
→ 收获
→ 种子与食物循环
```

其余实现应迁移、标记废弃或删除资源引用。

#### 验收标准

- 同一种植物只有一套成长数据。
- 天气、肥料和耕地倍率不会重复结算。
- 成熟后不会重复产出。
- 保存重载后成长进度一致。

---

### 8.6 遗迹和探索地点扩充

当前正式遗迹内容量明显不足。优先增加：

1. **猎人营地**：食物、皮革、狼群线索。
2. **废弃矿工营地**：矿物、工具和冶炼提示。
3. **坠毁舱或古代设施**：长期目标与稀有部件。

#### 设计原则

- 不继续盲目扩大世界面积。
- 每种地点必须拥有不同风险和奖励。
- 遗迹不能让玩家直接跳过完整发展阶段。
- 相同遗迹不能在近距离重复出现。

## P2：清理与后续优化

### 8.7 遗留与未完成代码清理

需要确认资源引用后处理：

- `Player.Act()` 直接抛出 `NotImplementedException`。
- `Mod_HealthPoints` 基本未实现，而正式生命系统是 `DamageReceiver`。
- `SceneChange.Interact_Update()` 仍抛出异常。
- `GameController.Load/Save()` 保留过时 TODO，而按键持久化由 `InputBindingService` 负责。
- `DamageReceiver.DropLoot()` 已有实现，但仍有过时 TODO。

处理方式应是：

- 活跃入口：正式实现或改为安全行为。
- 已被替代入口：标记废弃并移除资源引用。
- 纯死代码：确认无引用后删除。

不要只为了消除异常而补充没有设计依据的逻辑。

---

### 8.8 难度系统深化

难度不建议只使用敌人生命和伤害乘法，应影响：

- 死亡掉落。
- 敌人警觉范围。
- 夜间生态预算。
- 食物腐坏速度。
- 环境伤害宽容度。
- 存档回退规则。

该项应在生态、制作和农业稳定后进行。

- 大量新生产设施。

- 完整太空玩法。

开发原则：

> 在现有核心循环形成完整、可理解、可验证的体验前，不继续横向堆叠新系统。

## 11. 策划验收总则

每个新系统或优化都应回答：

1. 玩家为什么需要它？
2. 它解决了当前循环中的什么问题？
3. 玩家如何发现并理解它？
4. 它带来了什么明确收益？
5. 它是否与已有系统形成闭环？
6. 完成后如何客观验证好不好用？

如果一个功能不能服务于：

```text
生存
成长
探索
基地建设
长期目标
```

中的至少一项，就不应进入当前版本的优先开发范围。
