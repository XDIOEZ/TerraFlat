## 1. 系统定位

把当前机械动力系统从“机械专用世界”向上泛化为统一的 **MachineWorld**，并把现有落地工作方块逐步迁移到同一套纯数据实体架构中。

目标不是把所有功能拆成大量可组合小模块，而是统一：

- 世界实体身份与生命周期
- 放置 / 拆除
- 存档
- 空间查询
- 交互目标
- 表现加载 / 卸载
- 与机械动力的连接入口

工作台、熔炉等具体玩法仍保持领域内聚，不为了组合而拆散。

最终原则：

~~~text
背包 / 掉落 Item
        │
        │ 放置
        ▼
    MachineWorld
        │
        ├─ MachineEntity
        ├─ Processing
        ├─ Interaction
        ├─ Storage
        ├─ Presentation
        └─ MechanicalNetwork
                │
                └─ RPM / Torque / 传动拓扑

        │
        │ 拆除
        ▼
背包 / 世界掉落 Item
~~~

落地后的机器和工作方块不再以完整 Item + GameObject + MonoBehaviour 作为权威对象。

## 2. 核心架构

### 2.1 MachineWorld

将现有 MechanicalWorld 泛化为 MachineWorld。

MachineWorld 负责：

- 机器实体注册、查询、删除
- 世界作用域与生命周期
- 稳定 Entity ID
- 世界格位置
- 统一存档 / 恢复
- 机器交互目标查询
- 表现变化通知
- 机器休眠 / 唤醒调度

MachineWorld 不负责：

- 具体熔炼规则
- 具体工作台配方规则
- 机械扭矩求解细节
- UI 逻辑

禁止把 MachineWorld 写成新的巨型玩法类。

### 2.2 MachineEntity

所有落地工作方块使用统一实体表示。

首轮至少包含：

~~~text
MachineEntity
├─ Id
├─ Cell
├─ Definition
├─ Snapshot
├─ RuntimeState
└─ PresentationState
~~~

实体本身只保存稳定身份和运行状态。

工作台、熔炉、机械锤等差异行为由对应领域逻辑处理。

### 2.3 MechanicalNetwork 保持独立内聚

现有：

- MechanicalNetworkGraph
- RPM
- Torque
- 变速箱
- 离合器
- 端口
- 动力源
- 用力器

继续作为 MachineWorld 内部的机械动力子系统。

禁止拆成 RpmModule、TorqueModule、PortModule、GearModule 等大量细粒度运行时模块。

机械动力保持一套高内聚算法。

## 7. 机械动力与工作方块互通

机械动力作为 MachineWorld 内部子系统，不让具体工作方块直接了解机械网络内部结构。

禁止继续扩散：

~~~text
FurnaceLogic
    ↓
MechanicalWorld.GetXXX()
~~~

推荐通过明确的领域数据连接。

### 7.1 机械做功

机械动力输出：

~~~text
MechanicalDrive
├─ Rpm
├─ Torque
└─ Available
~~~

加工设备只读取自身最终可用动力。

例如：

~~~text
MechanicalNetwork
        ↓
机械锤 MachineEntity
        ↓
RecipeProcessor.Advance(work)
~~~

### 7.2 风箱与熔炉

机械风箱不要让熔炉直接查询机械网络。

改为：

~~~text
MechanicalNetwork
        ↓
Bellows Entity
        ↓
Airflow
        ↓
FurnaceLogic
~~~

熔炉只知道当前鼓风强度。

未来来源可以扩展为机械风箱、手动风箱、电动风箱或其它 MOD 风源，但熔炉逻辑不需要修改。

## 13. 架构约束

必须遵守：

- 实体是数据，不是 GameObject
- 系统负责批量逻辑，不让每个机器自己 Update
- 表现生命周期与实体生命周期分离
- 交互不以 Collider 作为权威对象查找方式
- 机械网络只负责机械网络
- 工作台逻辑保持工作台内聚
- 熔炉逻辑保持熔炉内聚
- 只有真正需要复用 / 替换的能力才抽公共接口

禁止：

- 为了组合而把机器拆成几十个小模块
- 创建第二套与机械世界平行的 WorkBlockWorld
- MachineWorld 直接塞入所有玩法细节
- 工作方块直接读取机械网络内部拓扑
- 新旧两套落地工作方块长期双写

## 16. Harmony 与 C# MOD 边界

- 保留普通托管 C# 领域类和具名方法，不把炉温、加工、伤害与机械规则编入 Burst 原生计算内核。
- 推荐补丁入口包括 `MachineWorld.CalculateWorkAmount/Execute`、`RecipeProcessor.Advance/Commit`、`FurnaceLogic.CalculateMaximumTemperature/ConsumeFuel/HeatAndProcess`、`WorkbenchLogic.PerformWork`、`MachineCombatBridge.ApplyDamage` 和 `MechanicalNetworkGraph.Solve`。推荐入口不是补丁白名单。
- `MachineLogicRegistry.Register` 注册整类机器业务，返回租约交给 `ManagedModContext.Track`；支持替换内置工厂，释放时不能复活已卸载的覆盖层。
- 清单显式声明 managed 入口和依赖；先核对玩家授权的代码 SHA256，之后才执行 `IManagedGameMod`。不运行未授权代码，不扫描并自动执行任意 DLL。
- `Initialize` / `ContentReady` / `Dispose` 分离；Harmony MOD 只撤销自己的补丁 ID。世界切换不能清空资源会话级注册；同名程序集变更不支持进程内替换，需重启。
- 当前目标为桌面 Mono。Android 仍保持 IL2CPP，不承诺同一托管 DLL 加载路径适用于 IL2CPP、Unity 原生方法或 Burst 机器码。
- 首轮代码交付包含作者示例和契约检查，但未自动下载、安装、授权或执行第三方 Harmony DLL；实际补丁及双端联机仍需单独验收。
